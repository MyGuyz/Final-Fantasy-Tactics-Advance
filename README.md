## ความรู้ทางเทคนิคที่ได้มาแล้ว (สำคัญที่สุดสำหรับคนทำต่อ)

### 1. ระบบเข้ารหัสตัวอักษร — พิสูจน์แล้ว ใช้ได้เลย

เกม**ไม่ใช้ ASCII** ใช้ตารางรหัสของตัวเอง 2 โหมด:

**โหมด multibyte** (ใช้กับข้อความทั่วไป) — คู่ไบต์ `0x80 XX`
```
A-Z = 0x80B0 - 0x80C9
a-z = 0x80CA - 0x80E3
```

**โหมด single-byte** (ใช้กับชื่อ ขึ้นต้นสตริงด้วย `0x01`) — ไบต์เดียว
```
A-Z = 0xB1 - 0xCA
a-z = 0xCB - 0xE4
```

**หลักฐานว่าถูกต้อง** — ถอดจาก ROM ได้ตรงกับชื่อในเกมเป๊ะ:
```
ที่ 0x55129F:  01 BD CB DC CD D2 CF 00           →  "Marche"
ที่ 0x5512C7:  01 BD D9 D8 DE CC D6 CB D8 CD 00  →  "Montblanc"
```

### 2. รหัสควบคุม

`0x40` คือ **prefix คำสั่งควบคุมสากล** (ตัวนี้สำคัญมาก เข้าใจผิดตอนแรกเสียเวลาไปเยอะ):

| ไบต์ | ความหมาย | สถานะ |
|---|---|---|
| `0x00` | จบสตริง | ✅ ยืนยัน |
| `0x01` | สลับเข้าโหมด single-byte | ✅ ยืนยัน |
| `0x40 0x73` | เว้นวรรค | ✅ ยืนยัน |
| `0x40 0x6E` | ขึ้นบรรทัดใหม่ | ✅ ยืนยัน |
| `0x40 0x70` + `0x40 0x63` | จบหน้า/รอกดปุ่ม แล้วเคลียร์กล่อง | ✅ ยืนยัน |
| `0x32` | **ฝังสตริงบีบอัด LZSS** (ดูข้อ 3) | ✅ ยืนยัน |
| `0x72 0xXX` | แทรกชื่อจากตาราง CRN | 🟡 จากเอกสาร ยังไม่ verify |
| `0x74 0xXX` | หน่วงเวลา X/10 วินาที | 🟡 จากเอกสาร ยังไม่ verify |

**เครื่องหมายวรรคตอนยังเป็นการเดา** (จาก context ไม่ได้ verify แบบตัวอักษร):
`{80E4}`→`.` `{80EC}`→`,` `{80FC}`→`:` `{80EB}`→`!` `{80F4}`→`'` `{80F6}`→`"` `{80EA}`→`?` `{80FE}`→`-`

### 3. ระบบบีบอัด — ถอดได้ 3 แบบ

| แบบ | tag | ใช้กับ | สถานะ |
|---|---|---|---|
| GBA LZ77 มาตรฐาน | `0x10` | กราฟิก (430+ บล็อก) | ✅ ถอดได้ |
| GBA LZ77 variant | `0x11` | มี 22 บล็อก มีข้อความแค่ 1 บรรทัด | ✅ ถอดได้ |
| **FFTA LZSS** | `0x01` | สตริงและกราฟิกบางส่วน | ✅ ถอดได้ (`tools/lzss01.py`) |
| **embedded LZSS** | `0x32` | **บทสนทนาเนื้อเรื่อง** | ✅ ถอดได้ |

โครงสร้าง embedded LZSS: `0x32 XX` + ขนาด 4 ไบต์ **big-endian** + ข้อมูลบีบอัด

> ⚠️ **บทเรียนสำคัญ:** ตอนแรกข้าม `0x32` ไปเฉย ๆ ทำให้**บทสนทนาเนื้อเรื่องหลักหายไปเกือบหมด** โดยไม่รู้ตัว — แล้ว coverage check ตอนนั้นก็บอกว่า "ครบแล้ว" เพราะมันตรวจแค่ pattern ที่เรานิยามเอง พอ implement ตัวถอดแล้วกู้คืนมาได้ 1,491 บรรทัด **อย่าเชื่อ coverage check ที่ตรวจจาก pattern ตัวเอง**

| Offset | เนื้อหา |

## ปัญหาที่ยังค้าง 2 เรื่อง

### ปัญหา 1: 394 บรรทัดยังถอดไม่ได้ (6.9% ของ 5,674 บรรทัดทั้งหมด)

รายการครบอยู่ที่ [`data/categorized_text/_INCOMPLETE_needs_work.txt`](data/categorized_text/_INCOMPLETE_needs_work.txt) พร้อม offset

**อาการ:** ถอดออกมาได้ครึ่ง ๆ เช่นที่ `0x4b0231` ควรเป็น "Those Nightwalkers..." แต่ได้ `Those Nigwaersut`

**สาเหตุ:** มีการบีบอัดอีกแบบที่ **ไม่มี marker `0x32`** ให้จับ

**เบาะแสที่หามาได้แล้ว (รอบแรก)** — เอาสองสตริงที่ขึ้นต้นเหมือนกันมาเทียบ:

| | A (`0x49b767`) | B (`0x49b407`) |
|---|---|---|
| ค่าที่เจอ | `A00B 9015 801F 8027 802B 802D` | `A00D 9017 8021 8029 802B 8031` |
| 12 บิตล่าง | 11, 21, 31, 39, 43, 45 | 13, 23, 33, 41, 43, 49 |
| 4 บิตบน | A, 9, 8, 8, 8, 8 | A, 9, 8, 8, 8, 8 |

B มีกลุ่มพิเศษแทรกเพิ่ม 1 ชุดตอนต้น แล้ว**ค่าทุกตัวหลังจากนั้นเพิ่มขึ้น +2 พอดีเป๊ะ** (11→13, 21→23, 31→33, 39→41)

→ แปลว่า 12 บิตล่างคือ **offset สะสม** = ลายเซ็นของ **back-reference แบบ LZ** ส่วน 4 บิตบนน่าจะเป็น length/type

**รอบสอง — ตรวจ raw byte จาก ROM ตรงๆ (ไม่ผ่าน placeholder decode) ที่ `0x49b767`/`0x49b407` แล้วพบเบาะแสใหม่ที่สำคัญ:**

```
0x49b767:  80 c8 80 d8 80 de 40 73 80 cc 80 ca 80 d7 80 f4 80 dd  = "You can't"
           a0 0b 40 db  80 01 42 e2 40 6e  90 15 40 e2  80 1f 40 d6  80 27 44 db ...
0x49b407:  80 c8 80 d8 80 de 40 73 80 cc 80 ca 80 d7 80 01 42 d8  80 dd a0 0d 40 db ...
```

สังเกตว่า **แทบทุกครั้งที่เจอ marker แบบ `[XX 0][val]` (เช่น `A0 0B`, `90 15`, `80 1F`) จะตามด้วย `40 XX` หรือ `44 XX` ทันที** — เดิมเข้าใจว่า `40 XX` เป็นแค่ control code แยกต่างหาก (ดูหัวข้อ "Control codes" — `0x40` เป็น prefix สากล) แต่ pattern ที่เกิดซ้ำสม่ำเสมอขนาดนี้ชวนสงสัยว่า **marker ตัวจริงอาจยาว 4 ไบต์ ไม่ใช่ 2 ไบต์** (เช่น `[type][val][40][param]`) — ลองถอดสมมติฐาน "2 ไบต์ = back-reference ตำแหน่งสัมบูรณ์ใน output ของสตริงเดียวกัน ยาว `type` ตัวอักษร" กับข้อมูลทั้ง 394 บรรทัดด้วยสคริปต์ (`tools/lzss01.py`-style decoder) แล้ว**ไม่ถอดออกมาเป็นภาษาอังกฤษที่อ่านรู้เรื่องได้เลย** (พังเป็น garbage ทุกกรณี) — สรุปว่าสมมติฐาน 2 ไบต์ตรงๆ ยังผิด ต้องมี field เพิ่มที่ยังไม่รู้ความหมาย (อาจเป็น `40 param` ต่อท้าย)

**ยังไม่รู้:** หน่วยของ offset (ไบต์ input? output? ตัวอักษร?), ความหมายที่แน่นอนของ 4 บิตบน, และความหมายของ byte คู่ `40 XX`/`44 XX` ที่ตามหลัง marker เกือบทุกครั้ง

**ทำไมยังไม่ใช้ทางลัด mGBA RAM-dump (ที่ใช้เจอฟอนต์ได้ผลมาแล้ว):** เช็ค region ของ offset ทั้ง 394 รายการแล้วพบว่า **ไม่มีสักรายการอยู่ในย่านที่เข้าถึงได้จากหน้าเมนูตอนบูตเครื่อง** (`system_ui`/`items`/`skills`) แบบที่ฟอนต์เจอง่าย — ทั้งหมดอยู่ใน `rumor_body` (256 รายการ, ข้อความกระดานข่าวลือ Ivalice), `story_dialogue` (129 รายการ, คัตซีน), และ `battle_log` (9 รายการ, ข้อความระหว่างต่อสู้) ซึ่งต้องเล่นผ่านการสร้างตัวละคร + ภารกิจเปิดเกมก่อนถึงจะเข้าถึงได้ — การกดปุ่มสุ่มแบบที่ใช้ตอนหาฟอนต์ (mash A/START เป็นจังหวะ) **ไปไม่ถึง** หน้าจอพวกนี้ในจำนวนเฟรมที่เหมาะสม ต้องมี save state ที่ผ่านภารกิจเปิดเกมมาแล้ว หรือสคริปต์ปุ่มกดแบบ TAS ถึงจะใช้ทางลัดนี้ได้จริง

**รอบสาม — ทดสอบสมมติฐาน 4-byte token + ค้นหา pointer table แบบ static (ตามคำแนะนำข้อ 2/3 ข้างบน):**

1. **จัดกลุ่ม token ทั้ง 394 บรรทัดเป็น marker (`[X0][val]`) + param (`[4Y][param]`) แล้วนับสถิติจริง:** เจอ marker ทั้งหมด 5,475 ครั้ง มีตัวตามด้วย param ทันที 4,407 ครั้ง (**80.5%** — ไม่ใช่ 100%) และ byte แรกของคู่ param ไม่ได้จำกัดแค่ `0x40`/`0x44` อย่างที่คิดตอนแรก — **ครอบคลุมเต็มช่วง `0x40`-`0x4F` ทั้ง 16 ค่า** (เป็น nibble field จริง ไม่ใช่แค่ 2-3 ค่าที่เห็นจากตัวอย่างสั้นๆ)
2. **ทดสอบ 4 สมมติฐานถอดรหัส** (self-reference ตำแหน่ง absolute/relative ผสมความยาวจาก nibble ต่างๆ, และตีความ param byte เป็นตัวอักษรผ่าน charmap ปกติ) กับข้อมูลจริงทั้ง 394 บรรทัด วัดด้วย dictionary คำศัพท์อังกฤษจริง (`/usr/share/dict/words`, 73,447 คำ) — **ทุกสมมติฐานได้ word-hit rate 32-35% ใกล้เคียงกันหมด** ซึ่งเป็นระดับ noise (ส่วนใหญ่มาจากข้อความส่วนที่ถอดถูกอยู่แล้ว เช่น "You"/"can"/"This" ไม่ใช่จากส่วนที่ถอดจาก marker) — **ยังไม่มีสมมติฐานไหนเข้าเป้าชัดเจน**
3. **ลองค้นหา pointer table แบบ static** (วิธีเดียวกับที่ใช้เจอฟังก์ชันฟอนต์ได้ผล) — สแกนทั้ง ROM หา 32-bit little-endian pointer ที่ชี้ตรงไปยัง `0x0849b767`/`0x0849b407`/`0x084b0231` (ที่อยู่ ROM ของ 3 สตริงตัวอย่าง) — **ไม่เจอเลยสักจุด** แปลว่าเกมไม่ได้เก็บ offset ของสตริงพวกนี้เป็น pointer ตรงๆ ในตาราง (ต้องคำนวณ/index แบบอ้อม เหมือนกับที่ฟอนต์เองก็หาไม่เจอด้วย static scan เช่นกัน) — เป็นหลักฐานเพิ่มเติมว่าโค้ดส่วนนี้ต้องอาศัย **dynamic analysis** ถึงจะไล่ต่อได้จริง เหมือนตอนหาฟอนต์

**สรุปสถานะ:** ทำ static analysis มาแล้ว 3 รอบ (เทียบ 2 สตริง → ทดสอบ 2-byte hypothesis กับทั้ง 394 บรรทัด → ทดสอบ 4-byte hypothesis + หา pointer table) ยังไม่เจอสูตรที่ถูกต้อง — เหมือนสถานการณ์ฟอนต์ก่อนหน้านี้ที่ static analysis หาไม่เจอจนกว่าจะใช้ dynamic analysis (mGBA watchpoint) ถึงเจอคำตอบ **ขั้นตอนถัดไปที่มีโอกาสสำเร็จจริงคือใช้ dynamic analysis เหมือนกัน** — แต่ติดที่ต้องมี save state ผ่านภารกิจเปิดเกมก่อน (ดูด้านบน) ถ้าไม่มี save state การเดา static ต่อแบบไม่มีหลักฐานยืนยันจากภายนอกมีความเสี่ยงสูงที่จะเข้าใจผิดซ้ำ (บทเรียนเดียวกับที่ CLAUDE.md เตือนไว้เรื่อง control code `0x32`) — แนะนำให้หยุดเดาต่อจนกว่าจะมี save state จริง

**ขั้นต่อไปที่แนะนำ:**
1. **สำคัญที่สุด:** หา/สร้าง save state ที่ผ่านภารกิจเปิดเกมแล้ว (เข้า World Map ได้) — ไม่ว่าจะเล่นเองแล้วเซฟ state ผ่าน mGBA GUI ปกติ หรือหา TAS input script ของ FFTA มาเล่นซ้ำแบบ headless — มีตัวนี้แล้วใช้ watchpoint แบบเดียวกับตอนหาฟอนต์ (ดูวิธีตั้ง watchpoint ท้ายหัวข้อ "ปัญหา 2") ดักตำแหน่ง ROM ของสตริงที่รู้ offset อยู่แล้วได้เลย จะได้คำตอบชัวร์ ไม่ต้องเดา
2. ถ้ายังไม่มี save state และอยากลอง static analysis ต่อ — ลองมองหาฟังก์ชัน decode ตัวจริงผ่านการ disassemble โค้ดรอบๆ ฟังก์ชันวาดข้อความที่รู้อยู่แล้ว (`0x080CB800` เป็นต้น จากปัญหา 2) เผื่อโค้ดเดียวกันนี้ยังใช้ decode ข้อความ battle_log/rumor_body ด้วย ไม่ใช่แค่ฟอนต์

### ปัญหา 2: หาฟอนต์ — 🟡 คืบหน้ามาก (เจอตำแหน่งจริงใน ROM แล้ว รอถอด compression scheme)

**อัปเดตล่าสุด:** ไล่ `LZ77UnCompVram` ครบ 5 จุดแล้วไม่เจอฟอนต์ (เจอแค่โลโก้/พื้นหลัง/สไปรต์ ตามที่บันทึกไว้เดิม) — ตัวเลข "58 จุด" ของ `LZ77UnCompWram` ที่เคยบันทึกไว้ไม่ถูกต้อง (สแกนจริงด้วย `find_bl_callers` เจอแค่ **19 จุด**) และ static analysis (ทั้ง brute-force pattern scan และ capstone disassembly) หาไม่เจอฟอนต์เลยแม้แต่บล็อกเดียวจากในบรรดา 3,371 บล็อก LZ77 มาตรฐาน + 615 บล็อก LZSS ของเกมเองที่ scan ได้ทั้ง ROM

**เปลี่ยนวิธีมาใช้ dynamic analysis แทน** — build mGBA core + Python bindings แบบ headless (ไม่ต้องมี GUI, compile จาก source เอง) รันเกมจริงพร้อม watchpoint ดักการเขียนหน่วยความจำ ผลที่ได้ (ยืนยันด้วยภาพจริงจาก VRAM ตอนรัน ไม่ใช่การเดา):

1. **ฟอนต์ไม่ได้เก็บเป็น tile sheet สำเร็จรูปแบบ LZ77/LZSS ธรรมดา** — มันถูก**ประกอบขึ้นที่ runtime ด้วย CPU** (ldrb/strb loop ทีละไบต์ ไม่ผ่าน BIOS decompress หรือ DMA) อธิบายได้ว่าทำไม static scan ทุกแบบถึงหาไม่เจอมาตลอด
2. **ข้อมูลต้นฉบับกลิฟอยู่ที่ ROM offset `0x08405EAA` เป็นต้นไป** (ยืนยันด้วย watchpoint จับ source-register ตอน CPU copy ทีละไบต์เข้า WRAM scratch buffer `0x02003CB0`) — แต่ **นี่ไม่ใช่จุดเริ่มตารางฟอนต์แน่ๆ** (น่าจะอยู่กลางตาราง เข้าถึงผ่าน index จาก charcode) ต้องหาจุดเริ่มตารางจริงเพิ่ม
3. **รูปแบบการบีบอัด — เจอแล้ว: คือ LZSS-01 ตัวเดียวกับที่มีอยู่แล้วใน `tools/lzss01.py`!** (อย่างน้อยส่วน opcode "literal copy") ตรวจสอบด้วยการดึง copy-run 236 ครั้งจาก watchpoint log มาเทียบกับสูตร `n = (ctrl_byte & 0x3F) + 1` เมื่อ `ctrl_byte & 0xC0 == 0x40` (เหมือน `tools/lzss01.py` บรรทัด `elif b & 0x40: cnt = (b & 0x3F) + 1`) — **ตรงสูตรครบ 236/236 รอบ ไม่มีข้อยกเว้น** แต่ตัว stream นี้**ไม่มี header `0x01` + ขนาด 4 ไบต์แบบมาตรฐาน** ก่อนหน้า (แปลว่าฟังก์ชันวาดฟอนต์เรียก decoder ตัวนี้ตรงๆ โดยรู้ขนาดปลายทางอยู่แล้วจากที่อื่น ไม่ต้องอ่าน header) — ตัวควบคุมไบต์แรกอยู่ที่ ROM `0x08405EA9` (ค่า `0x4E` = copy 15 ไบต์ พอดีกับ 15 ไบต์แรกที่เห็นจริงใน WRAM) — **ยังไม่ครบ:** ส่วน "skip/gap" ระหว่าง run (เช่น opcode `0x20`-prefix fill-zero หรือ back-reference `0x80`-prefix) ยังไม่ verify ครบ ลองรัน decoder เต็มรูปแบบ (เอา `lzss_decompress_ex` เดิมมาปรับให้ไม่ต้องอ่าน header) แล้วเจอ error ที่ back-reference opcode (`NEG_TMP80`) หลัง 39 ไบต์ — น่าจะเป็นเพราะ font render มีหลาย "pass" ทับกัน (เช่น outline + fill) ไม่ใช่ stream เดียวรวด ต้องแยกวิเคราะห์เพิ่ม
4. **ฟังก์ชันที่เกี่ยวข้อง** (ROM offset, ยืนยันด้วย disassembly จริงผ่าน capstone):
   - `0x0800555C–0x08005570` — byte-copy loop ตัวใน (อ่าน ROM → เขียน WRAM buffer)
   - `0x0800543C` — ฟังก์ชัน "วาดกลิฟ" ระดับกลาง (เรียก loop ด้านบน)
   - `0x080CB800–0x080CB8B4` — ฟังก์ชันวาดข้อความระดับสูง (เรียก `0x0800543C`)
   - ปลายทาง: WRAM scratch `0x02003CB0` → `CpuSet` (SWI `0x0B`) → VRAM `0x06009C00` / `0x06014800` / `0x06015800`
5. **ยืนยันด้วยตา:** render buffer WRAM ตอนแสดงหน้าจอ New/Load Game เห็นตัวอักษร "Aa" และข้อความ "New" "Ent(er)" "OK" ชัดเจน

**ขั้นต่อไป:** ใช้ watchpoint เดิมแต่ตั้งดักตั้งแต่ CPU เริ่มวาด**ตัวอักษรตัวแรกหลังบูตเครื่อง** (เร็วกว่านี้ในเกม) เพื่อไล่ backward หา index/pointer table ที่แปลง character code → offset ในตาราง และถอด RLE scheme ให้ครบ — วิธีการทั้งหมด (headless mGBA build + watchpoint) ใช้ซ้ำได้เลย ไม่ต้องเริ่มใหม่

**วิธี build mGBA headless เอง** (ไม่มีใน repo นี้ เพราะเป็น external tool ไม่ใช่โค้ดโปรเจกต์ — ต้อง clone/build ใหม่ทุกครั้งที่ session ใหม่):
```bash
git clone --depth 1 https://github.com/mgba-emu/mgba /path/to/mgba
cd /path/to/mgba && mkdir build && cd build
# ต้องมี: cmake, gcc/g++, swig, python3-dev, cffi (pip), cached_property (pip)
# และ libavcodec/avfilter/avformat/avutil/swscale/swresample -dev (สำคัญมาก — ไม่งั้น
# libmgba.so จะขาด symbol EReaderScanLoadImageA และ Python bindings import ไม่ขึ้น
# เพราะโค้ด e-reader scan ทั้งไฟล์ถูก #ifdef USE_FFMPEG ครอบไว้โดยไม่จำเป็น)
cmake -DBUILD_QT=OFF -DBUILD_SDL=OFF -DBUILD_PYTHON=ON -DBUILD_LTO=OFF ..
make -j$(nproc)
```
**กับดักที่เจอ** (เผื่อคนถัดไปเจอซ้ำ):
- ต้อง apt install ffmpeg dev libs ให้ครบ (`libavcodec-dev libavformat-dev libavutil-dev libswscale-dev libswresample-dev libavfilter-dev`) ไม่งั้น `USE_FFMPEG` จะเงียบๆ ปิดตัวเองแม้ตั้ง `ON` ไว้
- **ห้าม**เขียนโปรแกรม C ที่ include header ของ mgba โดยไม่ใส่ `-D` flag ชุดเดียวกับที่ build จริง (ดึงจาก `compile_commands.json`) — struct `mCore` มี field เปลี่ยนตาม macro พวกนี้ ถ้า `-D` ไม่ตรงจะได้ struct offset ผิด (`core->init` อ่านได้ค่า garbage แล้ว segfault) นี่คือบั๊กเดียวกับที่ cffi Python binding ของ mgba เจอ เพราะมันไม่ได้ parse header ด้วย macro ชุดเดียวกับตอน compile จริง — วิธีแก้คือเขียนโปรแกรม C คุยกับ `libmgba.so` ตรงๆ (ไม่ผ่าน Python binding) แล้วใส่ `-D` ให้ตรงเป๊ะ

**วิธีตั้ง watchpoint** (mGBA มี debugger API พร้อมใช้): `mDebuggerInit` → `mDebuggerAttach(core)` → สร้าง `mDebuggerModule` ของตัวเอง (ใส่ callback `entered`) → `mDebuggerAttachModule` → `platform->setWatchpoint(...)` ระบุช่วง address ที่จะดัก ตอน callback ทำงาน อ่าน register ได้จาก `((struct ARMCore*)core->cpu)->gprs[0..15]` (มี `ARM_PC`/`ARM_LR`/`ARM_SP` เป็น constant) แล้วต้องตั้ง `module->isPaused = false;` ก่อน return ไม่งั้นเกมจะหยุดค้าง

## วิธีใช้เครื่องมือ

ต้องมี Python 3 (ทดสอบบน 3.12) — ไม่ต้องลง dependency อะไรเลยสำหรับ 3 สคริปต์หลัก

```bash
# 1. สแกน ROM ดึงข้อความทั้งหมด → data/FFTA_corpus_raw.json
python tools/dump_corpus3.py

# 2. จัดหมวดหมู่ → data/categorized_text/*.txt + CATEGORIES_INDEX.md
python tools/categorize3.py

# 3. ออกรายงานข้อความที่ยังถอดไม่ได้ → _INCOMPLETE_needs_work.txt
python tools/gapreport.py
```

`dump_corpus3.py` ใช้เวลาสแกนพอสมควร (ไล่ทั้ง 16MB หลายรอบ) — รอได้

เรียกตัวถอดรหัสเองในโค้ด:
```python
from tools.lzss01 import lzss_decompress, lzss_decompress_ex

plain = lzss_decompress(rom_bytes, offset)          # คืนข้อมูลที่ถอดแล้ว
plain, used = lzss_decompress_ex(rom_bytes, offset) # คืนจำนวนไบต์ input ที่ใช้ไปด้วย
```
> `lzss_decompress_ex` จำเป็นตอนเดินสแกนต่อ เพราะต้องรู้ว่าบล็อกบีบอัดจบตรงไหน

**รูปแบบไฟล์ข้อความ:** `[offset]<TAB>ข้อความ` — มี `xN` ต่อท้าย offset ถ้าข้อความนั้นซ้ำ N ครั้งในเกม ใช้ offset อ้างอิงกลับ ROM ตอนแปะข้อความกลับ

**สองข้อในนั้นที่พิสูจน์แล้วว่าจริงมากในโปรเจกต์นี้:**

1. *"Text is glyph codes, not ASCII"* — ค้น ASCII ใน ROM นี้ไม่เจออะไรเลย ต้องผ่าน codec เท่านั้น
2. *"A lossy step inside the dumper can silently drop real text, and every check built on that corpus will agree it's fine"* — **เกิดขึ้นจริงกับโปรเจกต์นี้เป๊ะ ๆ** ตอนข้าม `0x32` ไป บทสนทนาเนื้อเรื่องหายเกือบหมดแต่ coverage check บอกว่าผ่าน เพราะมันตรวจจาก pattern ที่เรานิยามเอง

Skill ที่จะได้ใช้ในเฟสถัดไป (ยังไม่ได้เอามาใน repo นี้ อยู่ใน Claude Code):
- `complex-script-game-font` — ฝังฟอนต์ไทยลงในเกมที่ไม่มีฟอนต์ไทย (จัดการสระ/วรรณยุกต์ซ้อน)
- `game-text-localize` — แปลและแปะข้อความกลับเข้า ROM

## ข้อควรระวังสำหรับคนทำต่อ

1. **อย่า commit ROM** — `.gitignore` กันไว้แล้ว แต่เช็ค `git status` ก่อน commit ทุกครั้ง
2. **repo นี้เป็น private โดยตั้งใจ** เพราะข้อความในนี้เป็นงานลิขสิทธิ์ของ Square Enix — ถ้าจะเปลี่ยนเป็น public ให้คิดให้ดีก่อน
3. **offset ทุกตัวผูกกับ ROM เวอร์ชัน USA (SHA-1 ข้างบน)** เท่านั้น
4. **ภาษาไทยยาวกว่าอังกฤษ** — ตอนแปะข้อความกลับต้องดู byte budget ของแต่ละบล็อก และความกว้างกล่องข้อความ (ระบบมี `0x40 0x6E` ให้ขึ้นบรรทัดเอง)
5. **ยังไม่ได้แยกว่าอันไหนเป็นข้อความที่ฝังในกราฟิก** (เช่น โลโก้ ป้ายเมนูบางอัน) ซึ่งพวกนั้นต้องแก้เป็นรูปภาพ ไม่ใช่แก้ข้อความ
